1. Steps

  1. Open drivendata.org/competitions/306/competition-doe-gems/ and sign in.
  2. Click Submit (the submission form is on the competition page; the data page is separate).
  3. Choose gemsdoe50-seis-ridge-v1.tif. If the form rejects a bare GeoTIFF, upload gemsdoe50-seis-ridge-v1.zip instead — it contains exactly one GeoTIFF, which is the form the portal has accepted for this family before.
  4. Submission name: GEMSDOE50-SEIS-RIDGE-V1-5CAD91AC
  5. Note (optional) — paste verbatim: 
    GEMSDOE50 v1 | OADC lineation corridors from the official USGS ComCat catalogue (222,939 events, declustered) snapped to 3DEP lidar scarps; 45,000 dots, all off-catalogue; all cells finite in [0,1]
  6. Submit. Wait for the score. Record it in registry/submissions.json (see §4).

The portal error “Predicted values must be in range [0, 1]”. Two verified causes exist in this family of repositories: (a) the organisers’ training_features.tif carries the sentinel −3.4028235e+38 outside its valid area, so any raster assembled wholesale from it contains values near −1038; (b) NaN fails a numeric range test, because 0 <= nan <= 1 is false, so a validator that tests the whole array rejects the sample submission’s own NaN-outside encoding. This submission writes an explicit value in every cell of the grid: 1.0 on the 45,000 emitted dots, 0.0 everywhere else. Neither cause can apply.

3. What “success” looks like, honestly

  • Verified here: format; uniqueness; the metric algebra (tests/test_metric.py); the instruments; the predictive falsification test.
  • Not verified: any organiser score for this file. The expectation is “at or above the incumbent operating range” because the file beats the incumbent by 1.55× in credit per emitted cell on the only local instrument that ranks the 16 known live scores positively — but that instrument explains only part of the variance (leave-one-out Spearman 0.705, below this family’s own 0.80 bar), so a slot is a bet, not a certainty.
  • The one thing this file does that no prior file does: it puts mass on the 2020 Monte Cristo Range rupture trend from an independent physical signal. Every prior submission in the family covers ≈11 % of that trend with ≈0.0008 credit per cell; this file covers ≈36 % with 0.0022, and the predictive version of the detector (pre-2020 seismicity only) still covers 2.4 % while the smoothed-density controls cover nothing.

4. After the score arrives

  1. Append the score to registry/submissions.json (name, sha256, mass, score, date).
  2. Re-run python3 scripts/build_submission.py --name seis-ridge-v2 --mass 60000 and --mass 37654 to bracket the mass decision, and validate both with scripts/validate_candidate.py.
  3. Feed the new score into the ledger model on the analysis page; the two competing hidden-truth-size estimates (≈5,667 and ≈15,100 cells) are separated by exactly this kind of observation.
